# Business Studio — Developer Workspace

סביבת פיתוח פנימית למפתח לצורך אפיון, הקמה, שכפול וניהול של אפליקציות עסקיות עצמאיות.

> **ייעוד המאגר:** כלי העבודה של המפתח ותשתית Starter לפרויקטים עסקיים. האשף אינו מוצר ללקוחות קצה ואינו מערכת SaaS רב־דיירית.

## מה Business Studio אמור לאפשר

לתאר עסק ואת הצורך שלו בשפה חופשית, לקבל תוכנית הקמה ברורה, לבדוק את התשתיות וההרשאות, ואז לבצע הקמה מבוקרת של פרויקט נפרד — בלי לערבב קוד, נתונים או סודות בין לקוחות.

תהליך העבודה המתוכנן:

1. **אפיון העסק** — שם, תחום פעילות, קהל יעד, תהליך עסקי, דרישות, ערוצי תקשורת ומודולים.
2. **תכנון** — יצירת תוכנית Dry Run ובדיקת התאמת היכולות הקיימות לדרישות.
3. **Preflight** — בדיקת הרשאות, משאבים קיימים ותצורה מול GitHub, Neon ו־Render בקריאות בלבד.
4. **אישור** — הצגת פעולות ומשאבים שייוצרו; אין יצירת תשתיות או פעולות בעלות ללא אישור מפורש.
5. **הקמה** — יצירת Repository פרטי, מסד PostgreSQL נפרד ושירות Render נפרד, ככל שהחשבונות והמסלולים מאפשרים זאת.
6. **אימות** — בדיקות, CI, Health Check ובדיקת תוצאת הפריסה לפני דיווח על הצלחה.

## הפרדה בין סביבת המפתח לפרויקטי לקוחות

- Developer Studio מיועד למפתח בלבד.
- כל לקוח מקבל פרויקט עצמאי: Repository, מסד נתונים, שירות, הגדרות וסודות נפרדים.
- אין לשתף נתוני לקוחות, מפתחות API או משתני סביבה בין פרויקטים.
- אשף הפיתוח אינו נכלל באפליקציה שנמסרת ללקוח.
- אין לאמץ משאב ענן קיים על סמך שם בלבד; יש לוודא את זהותו והתאמתו.
- כשל באמצע הקמה אינו גורר מחיקה אוטומטית של משאבים שכבר נוצרו.

## אפליקציית Starter לניהול לידים

היישום העסקי הבסיסי שנוצר מה־Starter מתמקד בקליטת פניות ובניהול לידים:

- טופס פנייה באתר.
- תשתית WhatsApp inbound בכפוף להגדרת חשבון Meta וסודות.
- מסך CRM לניהול פניות, סטטוסים, משימות ומעקב טיפול.
- תיעוד מקור הפנייה והיסטוריית תקשורת.
- תשתית Outbox ו־Callback לאינטגרציות אוטומציה.
- הצעות עסקיות במצב המתנה לאישור; הפעלה דורשת פעולה אנושית מפורשת.

בחירת קטגוריית עסק אינה יוצרת יכולות שאינן קיימות בקוד. מודולים כגון מלאי, רכש, כספים, תורים או ניהול פרויקטים מחייבים פיתוח ואימות נפרדים לפני שניתן להציע אותם כחלק ממוצר פעיל.

## מצב המימוש והגבולות הידועים

| תחום | מצב / גבול |
|---|---|
| אשף הקמה למפתח | ממשק Web נפרד ותהליך CLI |
| תכנון ו־Dry Run | קיים |
| Preflight | מתאמי בדיקה לקריאה בלבד ל־GitHub, Neon ו־Render |
| הקמה אוטומטית | קוד ביצוע קיים; יש לאמת מול החשבונות בפועל לפני כל הקמה |
| GitHub → Render | ערוץ פקודות דרך Issues ו־GitHub Actions OIDC |
| אחסון מצב פקודות | Neon, בטבלת Inbox ייעודית |
| הצעות ואישורים | הצעה ממתינה; אין פקודת relay לאישור או להפעלת עסק |
| WhatsApp / Make / n8n / Gemini | דורשים חיבור חשבונות, הגדרות ובדיקות חיות; אין להניח ש־workflow חיצוני כבר פעיל |
| Canva | ניתן לעבוד דרך חיבור Canva המאומת ב־ChatGPT כאשר הוא זמין; אין OAuth עצמאי באשף |
| בדיקות | pytest ו־GitHub Actions; בדיקות עם mocks אינן הוכחה להקמה חיה |

**חשוב:** הצלחת בדיקות אוטומטיות אינה מוכיחה שחשבון חיצוני מחובר, שמשאב ענן נוצר, שהפריסה הסתיימה או שהשירות זמין. יש לבדוק כל אחד מהשלבים בפועל.

## ערוץ פקודות מאובטח: ChatGPT → GitHub → Render → Neon

הערוץ מאפשר להעביר פקודות מפתח ל־Business Studio בלי לחשוף תוכן עסקי גלוי ב־Issues של המאגר:

1. נפתחת ב־GitHub Issue פקודה ייעודית של Business Studio.
2. גוף הפקודה מכיל מעטפת מוצפנת בלבד.
3. GitHub Actions מופעל רק עבור פעולות של בעל המאגר, ומקבל GitHub OIDC token קצר־חיים.
4. Render מאמת את זהות GitHub, המאגר, ה־workflow וה־ref, מפענח את הפקודה ומריץ פעולה מתוך רשימת פעולות מורשית.
5. הפקודה והתוצאה נרשמות ב־Neon; התוצאה מוצפנת למפתח חד־פעמי ומוחזרת כתגובה מוצפנת ב־Issue.

ההצפנה מתבססת על RSA-OAEP-SHA256 לעטיפת מפתח AES אקראי ועל AES-256-GCM להצפנת התוכן. פרטים מלאים, פורמט ההודעות והגדרות Render מתועדים ב־[מפרט ערוץ הפקודות](docs/GITHUB_RENDER_COMMAND_RELAY_HE.md).

**גבולות אבטחה:** אין לשלוח סודות או מידע אישי גלוי ב־Issue. אין פקודת relay לאישור הצעה, להפעלת עסק או לשליחת webhook ל־Make. מפתח פרטי יציב ב־Render, אם מוגדר, חייב להישמר כ־Secret ולא בקוד או ב־GitHub.

## הפעלה מקומית ב־Windows PowerShell

דרישות: Git ו־Python 3.11 ומעלה. אין צורך בהרשאות מנהל להפעלה הרגילה.

אפשר להשתמש בסקריפט הראשי:

```powershell
git clone https://github.com/mv89-heb/business-mvp.git
Set-Location business-mvp
.\RUN-BUSINESS-STARTER.ps1
```

או להקים סביבת Python ולהריץ בדיקות:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pytest -q
```

הסקריפט מציע תפריט הכולל הכנה ובדיקות מקומיות, הפעלת האשף, Preflight לספקים והקמה חיה כאפשרות נפרדת. בדיקת ברירת המחדל אינה אמורה ליצור משאבי ענן.

### הפעלת ממשק האשף

הוראות מלאות ליצירת סיסמת מפתח וסוד Session, הגדרת משתני סביבה והפעלת האשף נמצאות ב־[מדריך אשף ההקמה](docs/DEVELOPER_PROVISIONING_WIZARD_HE.md).

במצב מקומי האשף מאזין ל־loopback בלבד. אין לחשוף אותו לרשת באמצעות שינוי host ל־`0.0.0.0`.

### Preflight והקמה חיה

- יש להריץ Preflight לקריאה בלבד לפני כל פעולה שמשנה תשתית.
- יש לוודא ידנית את החשבון, סביבת העבודה, הארגון, האזור, התוכנית והמכסה אצל כל ספק.
- אין להניח ש־Render או Neon יהיו ללא עלות; יש לבדוק את תנאי החשבון בפועל.
- הקמה חיה מחייבת אישור מפורש נוסף. אם לא ניתן לאמת עלות אפס, אין להמשיך במסלול שמחייב אפס עלות.
- במקרה של timeout בתהליך כתיבה, התוצאה עלולה להיות לא ידועה. אין לבצע retry עיוור או למחוק משאבים אוטומטית.

## פריסת אשף מרוחקת ואבטחה

לפריסת האשף בלבד יש להשתמש ב־`provisioning_wsgi:app` ולא ב־`wsgi:app`.

מצב Render דורש הגדרה מפורשת של `PROVISIONING_PUBLIC_ACCESS=true`, סיסמה אקראית באורך 32 תווים לפחות, `PROVISIONING_SESSION_SECRET` באורך 32 תווים לפחות ו־`PROVISIONING_ALLOWED_HOSTS` עם hostname מדויק. מצב זה כולל HTTPS, cookies מאובטחים, CSRF, Host allowlist, rate limiting ו־security headers.

יש להפעיל worker יחיד במצב מפתח הפקודות המבוסס על מפתח בזיכרון. הגנת סיסמה לבדה אינה תחליף ל־MFA או Zero Trust; מומלץ להגן על ממשק המפתח באמצעות Cloudflare Access או VPN לפני שימוש בפעולות ענן רגישות.

## ניהול סודות ופרטיות

- אין לשמור API keys, סיסמאות, מחרוזות חיבור או קובצי `.env` ב־Git.
- יש להעביר סודות דרך משתני סביבה או מנגנון Secrets של סביבת ההרצה.
- אין להדפיס סודות או payload מפוענח ללוגים, לדוחות או ל־Issues.
- טקסט חופשי מפרטי ליד אינו נשלח ל־Outbox כברירת מחדל. העברתו ל־Make/n8n לצורך סיווג AI מחייבת opt-in מפורש ובדיקת פרטיות.
- אין להעלות למאגר מידע עסקי אמיתי או נתוני לקוחות.

## בדיקות ואיכות

הרצת הבדיקות המקומיות:

```powershell
python -m pytest -q
```

GitHub Actions מריץ בדיקות Python ובדיקות נוספות המוגדרות ב־workflow. לפני מיזוג שינוי יש לבדוק את תוצאות ה־CI בפועל. בדיקות mocks מאמתות התנהגות קוד בתנאי בדיקה בלבד ואינן מחליפות בדיקת אינטגרציה מול חשבונות הספקים.

## עקרונות עבודה בפיתוח

1. לבדוק את המאגר, הענפים, ה־PR, ה־CI והשירותים לפני שינוי.
2. לעבוד בענף נפרד ולפתוח Pull Request.
3. לשמר נתונים, ארכיטקטורה קיימת והפרדה בין לקוחות.
4. להריץ בדיקות ולבדוק CI לפני מיזוג.
5. לקבל אישור מפורש לפני יצירת משאבי ענן, שינוי בעלות או מחיקה.
6. לא להמציא תוצאות, זמינות או סטטוס פריסה.
7. לדווח הצלחה רק לאחר אימות מול המקור בפועל.

## תשתיות בבעלות הלקוח

Business Studio מתוכנן כברירת מחדל להקים משאבים בחשבונות שבבעלות הלקוח, כאשר המפתח פועל בהרשאות מפורשות. אירוח בחשבונות המפתח הוא מסלול Managed נפרד שמחייב בחירה מפורשת. מסמך הארכיטקטורה והשלבים למימוש נמצא ב-[docs/CUSTOMER_OWNED_INFRASTRUCTURE_HE.md](docs/CUSTOMER_OWNED_INFRASTRUCTURE_HE.md).

**הערת מצב:** זהו יעד ארכיטקטוני מתועד; החיבורים וה-Provisioning הפר-לקוח עדיין דורשים מימוש לפני שניתן להפעיל הקמה בחשבונות לקוחות.
