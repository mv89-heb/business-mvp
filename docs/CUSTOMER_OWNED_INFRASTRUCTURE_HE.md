# ארכיטקטורת תשתיות בבעלות הלקוח

## החלטה מחייבת

ברירת המחדל של Business Studio היא **Customer-owned infrastructure**: כל לקוח הוא הבעלים של חשבונות הספקים והמשאבים שנוצרים עבורו. המפתח מפעיל את תהליך ההקמה בהרשאה מוגבלת ומפורשת, ומקבל הרשאת תחזוקה בהתאם להסכם.

המסלול החלופי הוא **Managed by developer**: המשאבים נוצרים בחשבונות העסק של המפתח. יש להציג אותו רק כשירות אירוח מנוהל שנבחר במפורש, עם הפרדת לקוחות, חיוב, גיבויים, SLA ויציאה מסודרת.

## גבולות בעלות

| רכיב | Customer-owned (ברירת מחדל) | Managed |
|---|---|---|
| GitHub Repository | ארגון/חשבון הלקוח | ארגון העסק של המפתח |
| Neon Project | ארגון Neon של הלקוח | ארגון Neon של המפתח |
| Render Service | Workspace של הלקוח | Workspace של המפתח |
| Domain / DNS | חשבון הלקוח | לפי הסכם השירות |
| Secrets וחשבונות צד שלישי | בבעלות הלקוח | מנוהלים עבור הלקוח בהפרדה |
| גישה למפתח | הרשאה ייעודית שניתנת וניתנת לביטול | הרשאת מפעיל פנימית |

## כלל אבטחה

אין להשתמש ב-`GITHUB_OWNER`, `NEON_ORG_ID` או `RENDER_WORKSPACE_ID` גלובליים כדי להקים לקוח במסלול Customer-owned. אין להשתמש ב-token אישי יחיד של המפתח עבור לקוחות שונים כברירת מחדל.

האשף לא ישמור API keys, OAuth access tokens, connection strings או סיסמאות לקוח בתוך:
- טבלת workflow state או audit;
- session של Flask או cookie;
- קובצי תוכנית, Dry Run, ZIP מסירה או Git;
- לוגים, הודעות שגיאה או נתוני Analytics.

סודות של לקוח יועברו רק דרך HTTPS, ישמשו בזיכרון למשימה המורשית, ויושמטו מתגובות HTML ומכל מצב מתמשך. עדיף OAuth / GitHub App installation tokens ו-delegated access במקום PAT קבוע. כאשר ספק אינו תומך במנגנון delegated access מתאים, יש להשתמש במפתח ייעודי בעל scope מינימלי, שהלקוח יכול לבטל.

## זרימת הקמה נדרשת

1. **בחירת בעלות** — ברירת מחדל Customer-owned; Managed דורש בחירה מפורשת ואישור תנאי אירוח.
2. **חיבור חשבונות** — חיבור נפרד ל-GitHub, Neon ו-Render. לכל חיבור נשמרים רק מזהי חשבון/ארגון/workspace לא סודיים, סטטוס, scopes ותאריך אימות.
3. **אימות הרשאות** — בדיקת זהות, הרשאות נדרשות, גישה לארגון הנבחר, region, מכסות ומחיר. אין להציג חיבור כתקין על סמך HTTP 200 בלבד.
4. **Dry Run** — מציג מי הבעלים, לאיזה חשבון כל משאב ייווצר, region, plan, עלות צפויה, הרשאות ופעולות.
5. **Preflight** — קריאה בלבד, מול חשבונות הלקוח בפועל. בדיקת כפילויות תחומה לחשבון/ארגון שאושר.
6. **אישור הקמה** — אישור מפורש נפרד ליצירת משאבים ולכל חיוב אפשרי. אין ליצור משאבים אם לא ניתן לאמת עלות אפס כאשר נדרש מסלול חינמי.
7. **Provisioning** — יצירה בחשבונות הלקוח, שמירת מזהי משאבים בלבד, בדיקות CI ו-Health.
8. **מסירה** — תיק מסירה ללא סודות, עם מזהי משאבים, בעלות, scopes, פעולות ביטול הרשאות והנחיות גיבוי.
9. **תחזוקה ויציאה** — הלקוח יכול לבטל הרשאות. יש לתעד אילו שירותים יפסיקו לעבוד לאחר הביטול ולספק export/backup לפני סיום שירות.

## התאמות ספקים

### GitHub
- יעד: GitHub App עם התקנה בארגון/חשבון הלקוח והרשאות Repository מינימליות.
- יצירת מאגר פרטי צריכה להתבצע בהקשר של ההתקנה והארגון שאושרו.
- PAT ידני הוא fallback זמני בלבד, לא ברירת מחדל ארכיטקטונית.
- יש לוודא שקוד היצירה תומך ב-GitHub App installation token ובארגון היעד, ולא להניח ש-`POST /user/repos` מתאים לכל סוג token.

### Neon
- יעד: OAuth או מנגנון API key ייעודי שנוצר על ידי בעל חשבון הלקוח, עם scope ארגוני מינימלי אם הספק תומך בכך.
- `NEON_ORG_ID` יהיה נתון פר-לקוח, לא משתנה סביבה גלובלי במסלול Customer-owned.
- חיפוש פרויקטים ויצירה יוגבלו תמיד ל-org ID שאושר.
- אין להניח ש-Free tier זמין או חינמי בכל חשבון; יש לאמת תנאים חיים לפני יצירה.

### Render
- יעד: חיבור Git Provider של הלקוח ל-Render, וביצוע פעולות דרך Workspace של הלקוח.
- `RENDER_WORKSPACE_ID` יהיה פר-לקוח.
- יש לוודא שה-Repository של הלקוח מחובר ל-Render לפני יצירת Web Service.
- יש לאמת תוכנית, אזור, הגדרות deploy ו-Health לפני סימון הצלחה.

## מודל נתונים מוצע

רשומת חיבור לכל לקוח ולכל ספק:
- `customer_id`, `provider`, `ownership_mode`;
- `external_account_id`, `organization_id`, `workspace_id` לפי הספק;
- `connection_method`, `granted_scopes`, `verified_at`, `expires_at`, `status`;
- הפניה ל-secret vault בלבד — לעולם לא ערך הסוד עצמו.

רשומת משאב:
- `customer_id`, `provider`, `resource_type`, `external_resource_id`, `region`, `plan`, `owner_account_id`, `created_at`, `health_verified_at`.

כל שאילתת איתור, שימוש חוזר או עדכון משאב חייבת להיות תחומה ל-`customer_id` ולחשבון הספק שאושר. אין לאמץ משאב קיים לפי שם בלבד.

## מצב המימוש הנוכחי — חשוב

הקוד הקיים עדיין משתמש במשתני סביבה גלובליים (`GITHUB_TOKEN`, `GITHUB_OWNER`, `NEON_API_KEY`, `NEON_ORG_ID`, `RENDER_API_KEY`, `RENDER_WORKSPACE_ID`) ובמתאמים שמקבלים credentials בעת יצירה. ממשק האשף כולל כעת בחירת בעלות, Customer-owned כברירת מחדל ו-Managed כבחירה מפורשת; Preflight ו-Provisioning חוסמים Customer-owned לפני כל קריאת ספק כדי למנוע fallback לחשבונות המפתח. **חיבורי לקוח פר-לקוח ו-Provisioning מלא עדיין אינם מיושמים**.

אין להציג את אשף ההקמה כמי שיוצר כבר עכשיו בחשבונות הלקוח. אין להעביר את `GITHUB_OWNER=mv89-heb` או מפתחות סביבת המפתח כברירת מחדל לתהליכי לקוח. יש להשלים את שלבי OAuth / delegated credentials, אחסון חיבורים מאובטח פר-לקוח, תחימת משאבים ואימות Preflight מול אותם חיבורים לפני הפעלת Customer-owned.

## שלבי מימוש

1. להפריד את מודל החיבורים מהגדרות הסביבה הגלובליות וליצור שכבת `ProviderConnectionResolver` פר-לקוח.
2. להוסיף GitHub App installation flow, כולל יצירה ופרסום של Repository בהקשר התקנה.
3. להוסיף Neon customer connection flow ותחימת org.
4. להוסיף Render customer connection flow ותחימת workspace.
5. להוסיף מסך בחירת בעלות, חיבור ספקים, scopes, בדיקות וחיווי מי הבעלים.
6. להעביר Preflight ו-Provisioning להשתמש רק בחיבורים שנבחרו ואומתו עבור הלקוח.
7. להוסיף בדיקות בידוד בין לקוחות, בדיקות שאין סודות ב-session/state/logs/export, ותרחישי revoke.
8. להשלים PR, CI, מיזוג ופריסת Render רק לאחר שכל הבדיקות עוברות.

## תנאי קבלה

- Customer-owned הוא ברירת המחדל ואי אפשר לבצע provisioning בלי חיבורי לקוח מאומתים.
- Managed דורש opt-in מפורש ואינו נבחר אוטומטית.
- אין fallback שקט לחשבונות המפתח.
- אין cross-customer discovery או reuse.
- כל סוד מוחזק מחוץ ל-workflow state, ל-session, ל-logs ול-exports.
- Dry Run ו-Preflight מציגים בעלות ויעד מפורשים ואינם מבצעים כתיבה.
- בדיקות אוטומטיות מוכיחות בידוד לקוחות, הרשאות מינימליות, fail-closed ו-revoke.
- לא נטען שההקמה הושלמה עד שיש מזהי משאבים ו-Health מאומתים בחשבון היעד.
